# Daybreak Blue + MPC — authorized bug bounty field operations

**Purpose:** This is the field-use track for approved bug bounty research in Codex/Daybreak, not another MPC source setup or a substitute classifier engine. The existing Machine Legal/BugTools canonical architecture, source owners, namespaces, method contracts, private Sites deployment, PASS receipts, Drive/Dash controllers and native program records remain authoritative.

## Capability boundaries

- **Model / sign-in:** In the actual Codex product surface, select the Daybreak Blue option offered to the signed-in user and record what the task itself identifies as its active model/access. A text prompt or checked-in config cannot turn Daybreak on, guarantee its Cloud availability, or transfer approved access to another identity/surface.
- **Security key:** A hardware security key protects access to the account. It is not a token for a bounty platform, not evidence of target scope, and must never be copied into the repository. Never copy authenticator secrets, API keys, session cookies, payout IDs, identity documents, or private credentials into GitHub.
- **Blue scope:** Daybreak Blue supports approved defensive vulnerability discovery, triage, review and patch validation. Separately approved Daybreak Red is designed for more advanced reproduction/exploit/pentest workflows. Do not infer Red approval from Blue selection. Official source: https://learn.chatgpt.com/docs/cyber-safety
- **Cloud:** A reusable Codex environment supplies tools/dependencies and isolated task workspaces. The verified fresh-task restoration receipt establishes source-build readiness, not target reachability, actual Daybreak selection, account authorization on a bounty platform, or live scan permission.
- **MPC:** Hosted MPC evaluates bounded caller-supplied records/models and does not itself test network targets, authenticate reports, retrieve live target evidence, promote findings, or publish a bounty report. The originating ChatGPT session can access MPC; separate Codex task exposure remains an independent observation.

## Mission: passive-first, payout-informed, adversarially verified

For one program and 1–3 source-owned candidate objects per PASS:

1. **Recover without regression.** Read the latest live program controller / canonical Drive-Dash pointer, prior submission state, exact PASS receipt, source IDs, preserved test logs and unresolved falsifier. Do not restart a completed bounty or substitute the original ZIP for newer native state. Resolve conflicting pointers as BLOCKED/READ_ONLY until reconciled.
2. **Establish the program rule card.** From the official, current bounty platform program rules, record: platform/program ID; captured date/version/locator; applicable countries/entities; explicit in-scope targets; out-of-scope targets; account constraints; passive/manual/automated permissions; request-rate ceiling; forbidden actions; testing window; data retention/deletion and confidentiality; reporting channel; disclosure restrictions; allowed test account and instrument(s). Identity proof is not program authorization. A rule card is data; independently restrict network/tools.
3. **Scope-isolated field workspace.** Keep evidence private and segregated by program. Use allowlisted hostnames and denied external destinations wherever supported, least-privilege permissions, short-lived test accounts, and review for sensitive actions. Do not assume the Cloud environment has target network access. Do not change production infrastructure or make real financial transactions unless the program explicitly permits the exact action. If an action is forbidden or not clearly allowed, do passive review or owned synthetic fixtures instead.
4. **Build source-bound object/atom model.** Source owner, exact native locator/version/time, subject identity, actor/capacity, input/state transition/output, money/authority/finality, channel, expected invariant, competing explanation, falsifier, known negative result and epistemic state. Preserve string/integer ID types and the 25 coordinates / 14 jacket axes. Link to existing MAXVAR/NESTMAX/BL/MBSS registries rather than inventing aliases.
5. **Apply existing intelligence.** For business logic, account for 32 BL branches/384 child checks. Select active methods *by dimensions and falsifiers* from the real hosted Method Ark; prefer high-impact candidate seams backed by current native evidence, not blind full-sweep execution. Use finite invariants, relational/identity/authority graphs, state/temporal comparisons, conservation/ledger checks, FTA/FMEA, metamorphic controls, adversarial hypothesis comparison and bounded atomic transformations where the caller can supply valid models. Method hooks not implemented are research specifications, never reported as executed checks.
6. **Test only a currently authorized minimum.** First use source-only / fixture / own-account comparison. For live target interactions, document the exact scope rule and limits, the smallest permitted action, a stop condition, what constitutes success/falsification, a responsible human approver for sensitive steps, and the expected evidence. Follow *each program's* automation and rate rules; never extrapolate Social Deal limits to KOMOJU or vice versa. Rate caps must be enforced by the actual tool/proxy (text instructions do not enforce them). Never touch third-party personal data, exfiltrate secrets, escalate to persistence, run destructive load or broaden scope.
7. **Separate test states.** PLAN != RUN; ATTEMPTED != OBSERVED; OBSERVED != AUTHENTICATED; COMPARISON != INVARIANT FAILURE; MODEL COUNTEREXAMPLE != TARGET VULNERABILITY; TECHNICAL EFFECT != VERIFIED SECURITY IMPACT; SUBMISSION != ACCEPTANCE != REWARD.
8. **Adversarial check.** Strongest benign explanation, alternate owner/tenant/config/version, cache/asynchrony, legitimate rate limit, expected business rule, UI-only inconsistency, duplicate report risk, temporal mismatch, record omission and inability to reproduce. Retain both positive and negative observations.
9. **Bounty-ready packet.** Build the NASA-inspired V&V matrix and source-owned report using `docs/nasa-inspired-bounty-verification-report.md`. Include authorized scope, evidence identity/hash/redaction, minimal reproduction, observed vs expected invariant, business/security consequence, failed alternatives, confidence limits and concrete remediation only when supported. Report actual payout only when platform establishes it, never use speculative severity as payout proof.
10. **Checkpoint and handoff.** Persist only changed state: PASS ID, canonical controller pointer, 1–3 objects, source owner/version/locator, method/registry IDs, tests run with exact permission, adverse falsifier, current readiness, unreconciled differences and next single bounded action. Preserve existing PASS style. Read-back verify saving when connected Drive/Dash is available. Never overwrite canonical source or submit/disclose externally without explicit user authorization.

## What Codex does versus what ChatGPT does

- **Codex with chosen Daybreak Blue:** run controlled field work *when supported in the actual task*: inspect authorized target-source artifacts/logs, model the business process, implement/execute synthetic local checks, and run expressly permitted live checks within independently enforced boundary. Record real command output, target response status, timestamps, exact policy and whether activity was passive, synthetic, or live. If tool/network/model access unavailable, mark UNAVAILABLE and do not simulate a target check.
- **ChatGPT + connected MPC tools:** coordinate classification, verify the method catalog and finite model input/output, compare Drive/Dash/native evidence, falsify candidate conclusions, compose the engineering report and track honest readiness. Cloud and ChatGPT are independent tool exposures.
- **GitHub:** MPC and BugLab development source, test fixtures and sanitized templates. No customer secrets or sensitive bounty artifacts.
- **Private Drive/Dash:** canonical and program-specific records, verified checkpoint pointers, restricted evidence and submitted report copies consistent with program confidentiality and retention requirements.
- **Production Sites:** existing private MPC service; deployments require a separate explicit decision and native reconciliation.
